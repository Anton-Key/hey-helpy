# Hey Helpy — контекст проекта для Claude Code

## Что это
Hey Helpy — ИИ-сервис эксплуатации зданий (CMMS / facility management): офисы, отели, склады.
Четыре функции продукта:
1. **Приём** заявок: текст, голос (ключевая фраза «Эй, Хелпи» / «Hey, Helpy»), фото с камеры.
2. **Отправка** нужному подрядчику по закреплённым слоям и объектам, разово или по графику планового ТО.
3. **Исполнение**: план этажа с маркерами, распознавание оборудования камерой, AR-метка с чек-листом.
4. **Контроль**: посещения по геозоне, время на объекте и на работе, фото «до/после», приёмка. Заявку нельзя закрыть без подтверждения.

Сейчас идёт MVP к демо-дню акселератора (октябрь 2026). Приоритет — работающий сквозной сценарий, а не полнота функций.

## Стек
- Flutter (мобильное приложение + веб), Dart ≥ 3.4. Пакеты: `supabase_flutter`, `go_router`, `flutter_localizations` + `intl` (переводы), `shared_preferences`, `record` (голос), `image_picker` + `geolocator` (фото).
- Backend: Supabase (Postgres + RLS + Auth + Storage), регион eu-west-1. Позже — self-hosted Supabase в Yandex Cloud для РФ.
- ИИ (план): Yandex SpeechKit (речь → текст), YandexGPT (разбор заявки), Picovoice Porcupine (ключевая фраза на устройстве).
- **MVP только под Android.** APK собирается GitHub Actions (`.github/workflows/build-apk.yml`), ключи — в секретах репозитория.
- Ключи Supabase передаются при запуске: `--dart-define=SUPABASE_URL=... --dart-define=SUPABASE_ANON_KEY=...`

- `lib/features/onboarding/` — создание компании / вступление по коду приглашения через RPC.
- `lib/features/requests/requests.dart` — заявки: список, карточка, форма, смена статусов.
- `lib/features/voice/` — голосовая заявка: запись, заглушка распознавания, экран подтверждения.
- `lib/features/photos/` — фото «до/после»: съёмка только камерой (`image_picker`, ~1600 px) с геометкой (`geolocator`), загрузка в Storage + `attachments`, блок в карточке и просмотр на весь экран.
- `lib/features/directory/directory.dart` — объекты, помещения, подрядчики, слои, закрепления (`Binding`), исполнители; `contractor_card.dart` — карточка подрядчика (закрепления с нормой визитов, исполнители, его заявки, отчёт); `object_card.dart` — карточка объекта (адрес, координаты и радиус геозоны, помещения, подрядчики, последние заявки).
- `lib/features/history/history_screen.dart` — «История»: принятые и отменённые заявки за период (под RLS).
- `lib/features/requests/order_list.dart` — общий список заявок (`WorkOrderListScreen`, `OrderTile`, `StatusPill`, `OrderContext`).
- `lib/core/ui.dart` — `TapCard` (нажимаемая карточка с эффектом нажатия и стрелкой), `ChoiceTag`, `SectionTitle`, `brandButtonStyle()`; `lib/core/period.dart` — период «неделя / 30 дней / месяц / свой» (по умолчанию 30 дней) и `PeriodBar`; `lib/core/paging.dart` — чтение страницами по 1000 строк.
- `lib/features/reports/` — отчёты по подрядчикам за период (только менеджер/админ, пункт меню скрыт для остальных): `report_repository.dart` читает данные под RLS и считает показатели, `reports_screen.dart` — экран; норма визитов — `contractor_layers.visits_per_month` (0010).
- `lib/features/profile/` — «Моя компания» (`company_screen.dart`: название, сотрудники и роли через `set_member_role`, приглашения `invites`), «Настройки» (`settings_screen.dart`: имя, телефон, пароль, язык, версия); `lib/core/language_picker.dart` — общий выбор языка, `lib/core/app_links.dart` — адрес сайта и ссылка-приглашение `?invite=`.
- `lib/features/notifications/` — уведомления за 14 дней по роли (из заявок и визитов под RLS), отметка «прочитано» на устройстве и в `profiles.notifications_seen_at` (0011); колокольчик в шапке.
- `lib/features/requests/contractor_picker.dart` — окно выбора подрядчика (закреплённые за слоем и объектом сверху, поиск); карточка заявки — главные действия в нижней панели.
- `lib/features/home/`, `auth/`, `lib/models/`.

## База данных (Supabase)
Миграции применяет только пользователь: GitHub Actions «Apply migration» с его одобрением или вручную в Supabase → SQL Editor (у Claude Code нет доступа к базе на запись, см. «Миграции»):
- **0003** — закрыта эскалация привилегий: `profiles.company_id` и `profiles.role` меняются только через RPC `create_company`, `accept_invite`, `set_member_role`. Индексы, `updated_at`.
- **0004** — слои (`layers`), закрепление подрядчиков (`contractor_layers`), автоназначение заявки подрядчику слоя, статусы, ролевой доступ к заявкам, таблица `visits`.
- **0005** — слой «Системы безопасности».
- **0006** — фото «до/после»: хранилище `work-photos` (путь `<company_id>/<work_order_id>/<файл>.jpg`), `attachments.stage` / `uploaded_by` / `mock_location`, доступ к вложениям как к заявке, «на проверку» только с фото «после», `requires_photo` включён у всех слоёв.
- **0007** — мультиязычность: `profiles.locale`, `layers.name_i18n`.
- **0008** — исправления безопасности из аудита: исполнитель меняет у заявки только статус, заявитель — только содержание своей; назначение, обязательное фото и приёмку — менеджер (триггер `trg_wo_guard`). Приглашения и справочники меняет только менеджер, срок приглашения 7 дней. Чек-листы и история — как сама заявка. Служебные функции закрыты от анонимов, новые функции по умолчанию закрыты для всех. Обязательное фото новой заявки — из слоя, не от приложения. Требует 0006.
- **0009** — отметка визита по геозоне: `objects.geofence_radius_m` (по умолчанию 150 м), у `visits` — `work_order_id`, `accuracy_m`, `distance_m`, `in_geofence`. Время, расстояние и флаг геозоны считает база (триггер `trg_visits_fill`); визит закрывается сам, когда заявка выходит из «в работе» (`trg_wo_close_visits`). Записать визит — только свой, по заявке в работе своего подрядчика.
- **0010** — отчёты: норма визитов в месяц у закрепления подрядчика (`contractor_layers.visits_per_month`), счётчик возвратов заявки `work_orders.return_count` (ведёт только база, триггер `trg_wo_return_count`), индекс визитов по дате.
- **0011** — профиль: `profiles.notifications_seen_at` (отметка «уведомления прочитаны»), переименование компании менеджером (политика `companies_update_manager`, право только на `name`), `set_member_role` разрешена и менеджеру (кроме назначения/смены администратора).

Статусы заявки: `new → assigned → in_progress → on_review → done` (принята) или `returned` (возвращена с `return_reason`), плюс `cancelled`.
Правила переходов проверяет триггер `trg_wo_status_flow` в базе:
- взять в работу и отправить на проверку — исполнитель подрядчика или менеджер;
- принять или вернуть — автор заявки или менеджер;
- если `requires_photo = true`, на проверку нельзя без фото **«после»** (`attachments.stage = 'after'`). Фото «после» загружает исполнитель (или менеджер) в статусе «в работе», фото «до» — автор (или менеджер) до закрытия заявки.

Роли: `admin`, `manager` (видят всё в компании), `requester` (свои заявки), `executor` / `contractor` (заявки своего подрядчика).
Вид работ в форме заявки = слой из таблицы `layers`. Приложение передаёт `layer_id` (и `work_type` = `layers.name`); триггер по слою и объекту назначает подрядчика.

## Миграции
Применённые миграции: 0001 0002 0003 0004 0005 0006 0007 0008 0009 0010 0011

(Номер в строку выше дописывается **только после** сообщения пользователя «применена NNNN» — это может сделать Claude Code или сам пользователь. Хук `protect_migrations.sh` запрещает менять файлы с этими номерами; workflow «Apply migration» не применяет номера из этой строки повторно.)

**Как применить миграцию — GitHub Actions с одобрением пользователя (основной способ):**
1. Файл `supabase/migrations/NNNN_….sql` уже запушен в `main`.
2. GitHub → **Actions** → **«Apply migration»** → **Run workflow** → в поле `file` — имя файла (например `0011_profile_company_notifications.sql`) → **Run workflow**.
3. Задача «Проверка и текст миграции» (без доступа к базе) проверяет имя `NNNN_*.sql`, что файл есть и что номера нет в «Применённых миграциях», и печатает полный текст файла. Прочитать его.
4. **Review deployments** → `production-db` → **Approve and deploy**. Задача «Применение» выполняет `psql "$SUPABASE_DB_URL" -v ON_ERROR_STOP=1 --single-transaction -f …`: при любой ошибке вся миграция откатывается. Итог — в Summary запуска.
5. Пользователь пишет Claude Code «применена NNNN» — только тогда Claude дописывает номер в «Применённые миграции».
- **Claude Code никогда не запускает, не перезапускает и не одобряет этот workflow** — никаких `gh workflow run`, `gh run rerun`, `gh api …/dispatches` или `…/pending_deployments` и т. п. Запускает и одобряет только пользователь.
- Запасной способ: Supabase → SQL Editor → New query → вставить весь файл миграции → Run (после этого так же «применена NNNN»).
- Настройка один раз: GitHub → Settings → Environments → `production-db`: Required reviewers — владелец репозитория, Deployment branches — только `main`, секрет окружения `SUPABASE_DB_URL` (Supabase → Connect → строка **Session pooler**, с паролем базы). Других секретов workflow не использует.

- Источник истины по схеме базы — папка `supabase/migrations/`. Файлы называются `NNNN_описание.sql` и применяются по порядку номеров.
- Миграции **0001–0011 уже применены вручную** через Supabase → SQL Editor (0001–0005 проверены 1 октября 2026, 0006–0009 — командой `/db` 7 октября 2026; 0010 применена 7 октября 2026; 0011 применена 7 октября 2026, проверена запросом к базе).
- Номера 0001–0011 заняты (см. список выше); следующая новая миграция — `0012_...`.
- ⚠️ В миграциях нет поля `work_orders.assigned_contractor_id`: в рабочей базе оно добавлено вручную, а 0004 на него опирается. Для чистой установки (например, self-hosted) его нужно добавить отдельной миграцией.
- Тестовые данные для демо — `supabase/seed/demo.sql` (не миграция), инструкция — `docs/DEMO_SETUP.md`. История за 30 дней для «Истории» и «Отчётов» — `supabase/seed/demo_history.sql` (запускать после demo.sql; триггеры выключает только внутри своей транзакции; блок удаления в начале).
- **Не запускать `supabase db push` без `supabase migration repair`**: CLI не знает, что 0001–0011 уже применены вручную, и попытается выполнить их повторно. Сначала отметить их как применённые: `supabase migration repair --status applied 0001 0002 0003 0004 0005 0006 0007 0008 0009 0010 0011`.
- `schema.sql` в корне — снимок базы (pg_dump) от 23 сентября 2026, сделанный **до** 0003: в нём нет слоёв, визитов и RPC онбординга. Только для справки, не применять и не считать актуальным.

## Языки (RU, EN; позже арабский)
- Все строки интерфейса — только через `lib/l10n/app_ru.arb` и `app_en.arb` (`context.l10n.ключ`), включая статусы, ошибки, подписи отчётов. Новый экран сразу пишется с переводами на оба языка.
- Даты и числа — через `intl` с языком интерфейса (`l10n.dateTime(...)`, `NumberFormat(..., l10n.localeName)`).
- Язык: сохранённый на телефоне → иначе язык устройства (ru/en) → иначе en. После входа приоритет у `profiles.locale`. Переключатель — в профиле.
- Справочники в базе хранят коды (`high`, `office`, `on_review`) — их переводит приложение. Слои — `layers.name_i18n` (`{"ru": ..., "en": ...}`), показ: перевод → `ru` → `name`. Заявка передаёт `layer_id`, чтобы назначение не зависело от языка. Названия объектов и помещений не переводим.
- Вёрстка под письмо справа налево: только `EdgeInsetsDirectional`, `AlignmentDirectional`, `PositionedDirectional`, `start/end` вместо `left/right`; стрелка «дальше» — `ChevronEnd` из `lib/core/directional.dart`.

## Правила работы
- **Не коммитить ключи, пароли и токены.** Никаких `.env` в git.
- Любое изменение базы — отдельный SQL-файл миграции в папке `supabase/migrations/` со следующим номером в имени (см. «Миграции»). Миграции должны безопасно запускаться повторно (`if not exists`, `drop ... if exists`). Права проверяются в базе (RLS и триггеры), а не только в интерфейсе.
- **После 0008 новые функции в базе по умолчанию закрыты для всех** (anon, authenticated). Каждую новую функцию миграция открывает явно: `revoke all on function public.f(...) from public, anon;` и, если её вызывает приложение (RPC) или она используется в политиках RLS, — `grant execute on function public.f(...) to authenticated;`. Без этого вызов из приложения или политика упадут с «permission denied». Триггерным функциям grant не нужен.
- После изменений Dart-кода запускать `flutter analyze lib` и исправлять ошибки.
- Перед `git push` — спросить разрешения у пользователя.
- Пользователь не программист: объяснять по-русски, простыми словами, пошагово.
- Интерфейс приложения — на русском и английском (см. «Языки»). Текст ошибок для пользователя — понятный, без технических деталей.

## Команды и хуки
Команды (`.claude/commands/`) вызываются вводом `/имя` в Claude Code:
- `/check` — перед каждым коммитом: анализ кода, тесты, веб-сборка, строки интерфейса вне `lib/l10n/`, правило названия «Эй, Helpy» / «Hey Helpy». Только отчёт.
- `/migration <название>` — когда нужно изменить базу: создаёт `supabase/migrations/NNNN_….sql` со следующим свободным номером и дописывает его в этот файл. В базе ничего не выполняет: миграцию применяет пользователь (Actions «Apply migration» или SQL Editor).
- `/db` — после применения миграций или если что-то не работает с данными: через Supabase MCP (только чтение) сверяет базу с файлами миграций, проверяет RLS и предупреждения безопасности.
- `/demo` — перед демо или показом: проходит сценарий заявка → назначение → фото «после» → возврат → приёмка → отчёт → язык и проверяет тестовые данные и трёх пользователей.

Хуки (`.claude/settings.json`, скрипты в `.claude/hooks/`) срабатывают сами, когда работает Claude Code:
- `dart_after_edit.sh` — после правки `.dart`-файла: `dart format` и `dart analyze` по нему. Ошибки и предупреждения возвращаются Claude, и он их сразу исправляет.
- `protect_migrations.sh` — запрещает менять или удалять файлы миграций, номера которых указаны в строке «Применённые миграции» (раздел «Миграции»). Нужно изменение — новая миграция.
- `block_workflow_dispatch.sh` — запрещает Claude запускать, перезапускать и одобрять GitHub Actions: `gh workflow run/enable`, `gh run rerun`, вызовы API `…/dispatches` и `…/pending_deployments` (в том числе с флагами `gh -R …` и в цепочках команд). Дублируется правилами `permissions.deny` в `.claude/settings.json`. Чтение (`gh run list/view/watch`) разрешено. Срабатывает и на эти слова внутри текста команды (например, в сообщении коммита) — их там не писать.
- `block_secrets.sh` — останавливает `git commit`, если в коммит попадают `env.json`, `*.env`, токен `sbp_…` или ключ service_role. Claude не обходит проверку, а сообщает пользователю.
Хуки не проверяют коммиты, сделанные руками вне Claude Code.

## Дизайн
- Бренд: мятный `#D8F0EA`, бирюзовый `#2DB89A`.
- На бирюзовых кнопках текст тёмно-зелёный `#06342A` (белый на бирюзовом не проходит по контрасту). Для ссылок и мелкого цветного текста — `#177A65`.
- В коде цвета — только из `HeyHelpyTheme` (`brand`, `onBrand`, `link`, `mint`), не из `colorScheme.primary`: в теме `primary` = `#177A65` (тёмно-зелёный, текст на нём белый) — им Flutter красит обычные кнопки и ссылки. Бирюзовая кнопка — `brandButtonStyle()`.
- Всё нажимаемое — с эффектом нажатия (`TapCard`, `InkWell` внутри `Material`, а не поверх `Container` с заливкой) и со стрелкой `ChevronEnd`, если открывает другой экран. Строка без действия — без стрелки.
- Цвета статусов отдельно от бренда: новая — жёлтый, в работе и на проверке — синий, срочная и возвращена — красный, принята — тёмно-серый с галочкой.
- Название продукта: в русском интерфейсе — **«Эй, Helpy»**, в английском — **«Hey Helpy»** (никогда просто «Helpy»). Берётся только из ключа `appName` в `lib/l10n/*.arb`, в коде не пишется.
