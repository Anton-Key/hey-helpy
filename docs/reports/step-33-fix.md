## Что случилось (простыми словами)
Refresh demo #16 (03.11.2026) остановился с ошибкой «duplicate key value violates unique constraint work_orders_plan_period_key», вся транзакция откатилась — база не изменилась.

У каждой регламентной задачи (ППР) есть план и период, и в базе запрещено иметь две задачи одного плана на один период. Сид каждый раз пересчитывает периоды «от сегодня»: задача 259 — «текущий месяц», 258 — «прошлый», 272 — «позапрошлый» и т. д. Postgres проверяет запрет **на каждой строке сразу**, а не в конце запроса. 30.10 задача 259 стояла на октябре. 03.11 сид обновляет сначала 258 («прошлый месяц» = теперь октябрь) — а 259 ещё держит октябрь → ошибка. Внутри одного месяца периоды не меняются, поэтому локально 30.10 всё проходило. Та же ловушка — у задач 261 / 260 против старых 234 / 241 и у 273 / 274 (ошибка в локальном повторе была как раз на `801, 2026-07-01`).

## Исправление
`supabase/seed/demo_history.sql`, блок 5e: перед вставкой задач периодов у всех задач планов 801–808 «Demo Properties» период снимается (`plan_id`, `period_start`, `period_end` = null), затем каждая задача получает свой период заново (как и раньше). Всё — в одной транзакции, промежуточное состояние никто не видит. Задача 279 (план 809) уже защищена: перед ней удаляются все прочие строки плана 809.

⚠️ Что решил и почему: вместо `on conflict (plan_id, period_start)` — снятие периодов. В одном `insert` можно указать только одну цель конфликта, а демо-задачам нужен `on conflict (id)` (постоянные id). Перестановка порядка строк не помогает при запуске «назад во времени». Снятие периодов работает при любом сдвиге дат. Чужих строк с этими планами нет: недемо-заявки «Demo Properties» удаляются в блоке 0, а план может быть только своей компании (триггер 0015). Задачи, которые `ppr_generate()` создал со случайными id после входа менеджера, тоже удаляются блоком 0.
