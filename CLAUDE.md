# Hey Helpy — контекст проекта для Claude Code

## Что это
Hey Helpy — ИИ-сервис эксплуатации зданий (CMMS / facility management): офисы, отели, склады.
Четыре функции продукта:
1. **Приём** заявок: текст, голос (ключевая фраза «Эй, Хелпи» / «Hey, Helpy»), фото с камеры.
2. **Отправка** нужному подрядчику по закреплённым слоям и объектам, разово или по графику планового ТО.
3. **Исполнение**: план этажа с маркерами, распознавание оборудования камерой, AR-метка с чек-листом.
4. **Контроль**: посещения по геозоне, время на объекте и на работе, фото «до/после», приёмка. Заявку нельзя закрыть без подтверждения.

Сейчас идёт MVP к демо-дню акселератора (октябрь 2026). Приоритет — работающий сквозной сценарий, а не полнота функций.

## Стек
- Flutter (мобильное приложение + веб), Dart ≥ 3.4. Пакеты: `supabase_flutter`, `go_router`, `flutter_localizations` + `intl` (переводы), `shared_preferences`, `speech_to_text` (голос → текст средствами платформы), `image_picker` + `geolocator` (фото), `flutter_map` + `latlong2` (карта объектов).
- Backend: Supabase (Postgres + RLS + Auth + Storage), регион eu-west-1. Позже — self-hosted Supabase в Yandex Cloud для РФ.
- Речь → текст сейчас — средствами платформы (Web Speech API в браузере, системный распознаватель на Android), без ключей. ИИ: YandexGPT разбирает заявку в Edge Function `voice-intake` (шаг 12, см. «Edge Functions»), позже Yandex SpeechKit для РФ, Picovoice Porcupine (ключевая фраза на устройстве).
- **MVP только под Android.** APK собирается GitHub Actions (`.github/workflows/build-apk.yml`), ключи — в секретах репозитория. После каждого пуша в `main` свежий APK лежит по постоянной ссылке (релиз `latest-apk`, перезаписывается): https://github.com/Anton-Key/hey-helpy/releases/download/latest-apk/hey-helpy.apk
- Ключи Supabase передаются при запуске: `--dart-define=SUPABASE_URL=... --dart-define=SUPABASE_ANON_KEY=...`

## База данных (Supabase)
Миграции применяет только пользователь: GitHub Actions «Apply migration» с его одобрением или вручную в Supabase → SQL Editor (у Claude Code нет доступа к базе на запись, см. «Миграции»):
- **0003** — закрыта эскалация привилегий: `profiles.company_id` и `profiles.role` меняются только через RPC `create_company`, `accept_invite`, `set_member_role`. Индексы, `updated_at`.
- **0004** — слои (`layers`), закрепление подрядчиков (`contractor_layers`), автоназначение заявки подрядчику слоя, статусы, ролевой доступ к заявкам, таблица `visits`.
- **0005** — слой «Системы безопасности».
- **0006** — фото «до/после»: хранилище `work-photos` (путь `<company_id>/<work_order_id>/<файл>.jpg`), `attachments.stage` / `uploaded_by` / `mock_location`, доступ к вложениям как к заявке, «на проверку» только с фото «после», `requires_photo` включён у всех слоёв.
- **0007** — мультиязычность: `profiles.locale`, `layers.name_i18n`.
- **0008** — исправления безопасности из аудита: исполнитель меняет у заявки только статус, заявитель — только содержание своей; назначение, обязательное фото и приёмку — менеджер (триггер `trg_wo_guard`). Приглашения и справочники меняет только менеджер, срок приглашения 7 дней. Чек-листы и история — как сама заявка. Служебные функции закрыты от анонимов, новые функции по умолчанию закрыты для всех. Обязательное фото новой заявки — из слоя, не от приложения. Требует 0006.
- **0009** — отметка визита по геозоне: `objects.geofence_radius_m` (по умолчанию 150 м), у `visits` — `work_order_id`, `accuracy_m`, `distance_m`, `in_geofence`. Время, расстояние и флаг геозоны считает база (триггер `trg_visits_fill`); визит закрывается сам, когда заявка выходит из «в работе» (`trg_wo_close_visits`). Записать визит — только свой, по заявке в работе своего подрядчика.
- **0010** — отчёты: норма визитов в месяц у закрепления подрядчика (`contractor_layers.visits_per_month`), счётчик возвратов заявки `work_orders.return_count` (ведёт только база, триггер `trg_wo_return_count`), индекс визитов по дате.
- **0011** — профиль: `profiles.notifications_seen_at` (отметка «уведомления прочитаны»), переименование компании менеджером (политика `companies_update_manager`, право только на `name`), `set_member_role` разрешена и менеджеру (кроме назначения/смены администратора).
- **0012** — проверочная, **ничего не меняет**: только `select` (пользователь, время, число компаний). Нужна, чтобы проверить workflow «Apply migration» (секрет, окружение `production-db`, одобрение). Без `begin/commit` — workflow сам оборачивает файл в транзакцию.
- **0013** — планы этажей (шаг 14a, применена 9 октября 2026): таблица `floors`, у `locations` и `assets` — `floor_id`, `plan_x`, `plan_y`, `plan_shape`; закрытый бакет `floor-plans`. Подробно — «Планы этажей (данные)».
- **0014** — исправление политик хранилища `floor-plans` (применена пользователем вручную через SQL Editor 10 октября 2026): в `floor_plans_insert` / `floor_plans_update` из 0013 внутри `exists (select … from public.floors f …)` стояло `storage.foldername(name)` — Postgres брал `f.name` («1 этаж»), а не путь файла, и любая загрузка плана отклонялась (`new row violates row-level security policy`). Теперь явно `objects.name`. Меняет только эти 2 политики, повторный запуск безопасен. Применена вручную через SQL Editor 10.10.2026, номер внесён в «Применённые» в шаге 16.

- **0015** — ППР, регионы и страны, реестр оборудования, номера помещений (шаг 16): таблицы `regions` (уникальность по `norm_name` внутри компании) и `maintenance_plans` (период `month | quarter | half_year | year | days`, чек-лист, `active`); у `objects` — `country_code` (ISO, только `^[A-Z]{2}$`), `city` (заполнен из адреса), `region_id`; у `locations` — `code` (уникален в объекте без учёта регистра); у `assets` — `layer_id`, `manufacturer`, `model`, `serial_no`, `installed_at`; у `work_orders` — `plan_id`, `period_start`, `period_end` (уникально `(plan_id, period_start)`), канал `ppr`. Политики объектов, помещений, этажей, оборудования, заявок, визитов, подрядчиков, закреплений, планов ППР, регионов и файлов планов — компания первой, зона второй; изменение — отдельными политиками insert / update / delete (**«for all» даёт и чтение**). В компании без администратора им становится первый менеджер (у «Демо БЦ» — демо-менеджер). Сохранение одной транзакцией (шаг 18): `set_member_zones(p_profile, p_zones jsonb)`, `save_crew(p_id, p_contractor, p_name, p_executors uuid[], p_zones jsonb)` — security invoker, права те же политики. Откат ограничений: `delete from access_zones; delete from crew_members;`.

Статусы заявки: `new → assigned → in_progress → on_review → done` (принята) или `returned` (возвращена с `return_reason`), плюс `cancelled`.
Правила переходов проверяет триггер `trg_wo_status_flow` в базе:
- взять в работу и отправить на проверку — исполнитель подрядчика или менеджер;
- принять или вернуть — автор заявки или менеджер;
- если `requires_photo = true`, на проверку нельзя без фото **«после»** (`attachments.stage = 'after'`). Фото «после» загружает исполнитель (или менеджер) в статусе «в работе», фото «до» — автор (или менеджер) до закрытия заявки.

Роли: `admin` (всё в компании, сотрудники и зоны), `manager` (вся компания или своя зона доступа, 0016), `requester` (свои заявки), `executor` / `contractor` (заявки своего подрядчика; в бригаде — только зоны бригады).
Вид работ в форме заявки = слой из таблицы `layers`. Приложение передаёт `layer_id` (и `work_type` = `layers.name`); триггер по слою и объекту назначает подрядчика.

## Голосовая заявка
- Кнопка «Нажми и говори» → `VoiceRecordScreen`: распознавание начинается сразу, текст виден по ходу речи. Стоп — «Готово», пауза 3 с или 30 с. Язык речи — по языку интерфейса (`ru-RU` / `en-US`).

## Правила работы
- **Не коммитить ключи, пароли и токены.** Никаких `.env` в git.
- Любое изменение базы — отдельный SQL-файл миграции в папке `supabase/migrations/` со следующим номером в имени (см. «Миграции»). Миграции должны безопасно запускаться повторно (`if not exists`, `drop ... if exists`). Права проверяются в базе (RLS и триггеры), а не только в интерфейсе.
- **После 0008 новые функции в базе по умолчанию закрыты для всех** (anon, authenticated). Каждую новую функцию миграция открывает явно: `revoke all on function public.f(...) from public, anon;` и, если её вызывает приложение (RPC) или она используется в политиках RLS, — `grant execute on function public.f(...) to authenticated;`. Без этого вызов из приложения или политика упадут с «permission denied». Триггерным функциям grant не нужен.
- После изменений Dart-кода запускать `flutter analyze lib` и исправлять ошибки.
- **Edge Functions не выкладывать и секреты не задавать** (ни Supabase CLI, ни API): выкладывает пользователь через workflow «Deploy functions» (см. «Edge Functions»). Значения ключей не писать в код, логи и отчёты.
- `git push` — только ветки шага `step-N` в конце шага (см. «Порядок работы»). В `main` не пушить никогда; любой другой push — спросить разрешения у пользователя.
- Пользователь не программист: объяснять по-русски, простыми словами, пошагово.
- Интерфейс приложения — на русском и английском (см. «Языки»). Текст ошибок для пользователя — понятный, без технических деталей.

## Обязательный порядок работы над каждым шагом
Действует для каждого шага начиная с 16 и важнее остальных пунктов, если они противоречат.
1. **Без вопросов.** Пользователь может не отвечать часами. Спорное решать самому, разумно, и записывать в отчёт с ⚠️ («что решил и почему»). Ничего не ждать от пользователя; исключение — необратимые действия: подготовить всё, описать в отчёте, самому не делать.
2. **Отчёт создаётся первым коммитом шага** (`docs/reports/step-N.md`): чек-лист блоков, раздел «Журнал» и раздел «Где остановился».
3. **Сохранять прогресс на случай обрыва сессии**: после каждого законченного куска (не реже чем каждые ~30–45 минут работы) — `/check` (или хотя бы `flutter analyze lib` и затронутые тесты) → коммит «Шаг N (блок): …» → `git push` ветки шага. В «Журнал» — строка «время · что сделано · коммит», в «Где остановился» — что делается сейчас и что следующим (файлы, функции, незакрытые проблемы).
4. **Продолжение после обрыва** (`claude --continue`, новая сессия или сжатие контекста): сначала прочитать `CLAUDE.md` и отчёт текущего шага, `git status` / `git log`, продолжить с «Где остановился».
5. **Если что-то падает 3 раза подряд** по одной причине — обойти, записать в отчёт, идти дальше. Не застревать.
6. **Итоговый отчёт обязателен даже при незаконченной работе**: что сделано, что нет и почему, ⚠️ решения, файлы, проверки, «Что сделать вам», «Как проверить руками», ограничения. PR — готовый к проверке, со ссылкой на отчёт.
7. Последние строки ответа — ссылка на PR и путь к отчёту.

## Порядок работы (с шага 9 — всегда)
`main` защищён: изменения попадают туда только через Pull Request, прямой push отклоняется.
1. **Перед началом шага** — `gh issue list --state open`: показать пользователю список открытых задач. Какие брать в шаг — решает пользователь (если он не ответил — см. «Без вопросов» выше: записать список в отчёт и взять то, что относится к заданию).
2. Каждый шаг — в ветке `step-N` от свежего `main` (`git switch main && git pull && git switch -c step-N`).
3. **В конце шага**: `/check` → `/screens` → отчёт `docs/reports/step-N.md` (коммитится в ветку). В отчёте:
   - что сделано, по пунктам задания;
   - новые и изменённые файлы — по строке на файл;
   - результат `/check` и `/screens` (что не открылось — с причиной);
   - **полный текст** новых миграций с объяснением: зачем, что меняет, безопасно ли запускать повторно;
   - что пользователю проверить в приложении;
   - ограничения и что не сделано.
4. Commit → push ветки `step-N` → `gh pr create --base main` (на каждый PR GitHub сам запускает «PR check», задача `check`: анализ, тесты, веб-сборка, имена миграций — `.github/workflows/pr-check.yml`): заголовок «Шаг N: …», в описании — короткая выжимка, ссылка на `docs/reports/step-N.md`, номер новой миграции (если есть), `Closes #N` для каждой закрытой задачи.
5. В `main` напрямую не пушить и PR самому не мержить — мержит пользователь после проверки.
6. Миграции не применять: пользователь применяет их кнопкой Actions → «Apply migration» после merge (см. «Миграции»).
7. Последняя строка ответа в терминале — номер и ссылка на PR, например: `PR #12: https://github.com/Anton-Key/hey-helpy/pull/12`.

Дублируется правилами `permissions.deny` в `.claude/settings.json`. Чтение (`gh run list/view/watch`) разрешено. Срабатывает и на эти слова внутри текста команды (например, в сообщении коммита) — их там не писать. Так же запрещает команды Supabase CLI `functions deploy`, `secrets set/unset`, `link`, `login` (и через `npx`) — правку файлов с этими словами делать через Edit/Write, а не через Bash.
- `block_secrets.sh` — останавливает `git commit`, если в коммит попадают `env.json`, `*.env`, `.env.demo`, пароли `DEMO_…_PASSWORD=…`, токен `sbp_…`, ключ service_role или картинки/PDF (`*.png`, `*.jpg`, `*.jpeg`, `*.webp`, `*.pdf`) вне `docs/screens/`, `docs/design/`, `assets/`, `tools/screens/` и значков приложения (`android/app/src/main/res/`, `web/`). Claude не обходит проверку, а сообщает пользователю.
Хуки не проверяют коммиты, сделанные руками вне Claude Code.
