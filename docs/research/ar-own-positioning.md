# Своя технология привязки к оборудованию в пространстве: V0 → V1 → V2

Шаг 31, 22.10.2026. Решение владельца продукта (20.10.2026): карты помещений, снимки и метки клиентов хранятся только у нас (позже — в стране клиента или у самого клиента), а не на серверах Niantic или Google. Эксперимент Niantic (шаг 28, отдельный VPS-APK, `docs/research/vps-niantic.md`) остаётся эталоном для сравнения и не меняется.

| Версия | Что умеет | Где хранится место | Статус |
|---|---|---|---|
| **V0** | Навёл телефон → «Что это?» → ИИ узнал оборудование → табличка висит над ним, пока ходишь по комнате | Нигде: метки живут, пока открыт экран | **Сделано в шаге 31** |
| V1 | Метки сохраняются; при следующем входе телефон сам находит их по кадрам (без «Что это?») | У нас: «отпечатки» места рядом с меткой | План |
| V2 | Полный свой VPS: 3D-карта помещения, точное положение телефона с первых секунд | У нас / в стране клиента / у клиента | План |

## V0 — как устроено

```
Телефон (Android, ARCore)                            Наш Supabase                    Yandex AI Studio
──────────────────────────                           ─────────────                   ────────────────
камера ARCore → картинка на экране, плоскости,
точки глубины (всё на телефоне)
«Что это?»:
  1. hit-test в точке прицела → временный якорь
  2. кадр → JPEG ≤ 1280 px ─────── JWT пользователя ──▶ photo-identify ── кадр ──▶ модель Qwen:
                                                     (реестр под RLS)  ◀─ вид, система, рамка
                                  ◀── вид, кандидаты, рамка ──  «какая это единица» решает функция
  3. один уверенный кандидат → табличка над якорем
     несколько → «Что это? Выберите оборудование»
  4. есть рамка → якорь переносится в её центр
     (луч из позы камеры в момент снимка)
  5. журнал узнаваний 0017 ───────────────────────────▶ photo_identifications (без фото)
табличка — обычный View; ARCore держит якорь,
PoseMath.project пересчитывает его в точку экрана каждый кадр
```

- **Экран** — нативный (`android/arlabel/`, `ArLabelActivity`), в основном APK. Камеру рисуем сами (GLES 2, `BackgroundRenderer`), без SceneView / Filament, — APK вырос на ~0,74 МБ (ARCore SDK и наш код; 77,20 → 77,94 МБ), а не на десятки.
- **Общее с VPS-экспериментом** вынесено в `android/arcommon/`: математика поз и проекции (`PoseMath`, плюс обратная матрица и луч через точку экрана), запросы к Supabase с JWT пользователя (`SupabaseRest`), тексты и цвета (`ArTexts`), табличка (`LabelCard`). VPS-модуль подключает его и работает как раньше.
- **Мост** — канал `hey_helpy/arlabel` (`ArLabelHook.kt`): `status` (есть ли ARCore, разрешена ли камера), `open` (контекст «Где я», язык, роль, JWT, адрес базы, anon-ключ, подписи табличек, все тексты из `.arb`). Своих строк в Kotlin нет.
- **Подписи табличек** готовит Flutter под RLS пользователя: оборудование объекта, количество открытых заявок (без ППР), ближайшее ТО — своё, иначе системы на объекте (как «Камера-помощник»). Текст «1 открытая заявка · ТО до 31.10» / «ТО просрочено» собирает Kotlin по шаблонам из `.arb` (`ArLabelLogic.factsLine`, формы числа RU / EN).
- **Уверенный кандидат** — единственный или опережающий второго на 0,15 балла функции (то же помещение против соседнего этажа — уверенно; два одинаковых кондиционера в одной комнате — выбор человеком).
- **До 10 табличек**: повторное «Что это?» по тому же оборудованию переставляет табличку (`LabelSlots`), одиннадцатая вытесняет самую старую.
- **Касание таблички**: «Карточка оборудования» (экран закрывается, Flutter открывает карточку), «Создать заявку» (форма с объектом, помещением, оборудованием, системой, заголовком и описанием от ИИ; снимок — фото «до», канал `camera`), «Убрать метку».
- **Камера и ARCore работают только пока экран на виду** (`onPause` — стоп, выход — всё освобождается).

### Что уходит с телефона и куда

| Данные | Куда | Хранится? |
|---|---|---|
| Кадр JPEG ≤ 1280 px (только по «Что это?») | Наша Edge Function `photo-identify` → Yandex AI Studio (модель `qwen3.6-35b-a3b`) | **Нет.** Функция не сохраняет и не логирует снимок (в логе — размер, время, модель, «рамка: да/нет»). |
| Итог узнавания: вид, уверенность, первый кандидат, выбор человека, модель, время | Наша база, `photo_identifications` (0017) | Да, **без фото и шильдика** — чтобы считать точность V0. |
| Снимок для фото «до» | Только если человек сам нажал «Создать заявку»: временный файл в `cache` приложения → Flutter читает и сразу удаляет → вложение заявки в нашем Storage | Как любое фото «до» заявки. |
| Позы, плоскости, облако точек ARCore | Никуда — остаются на телефоне | Нет (после закрытия экрана меток нет). |

**ARCore — только на телефоне.** В конфигурации сессии явно выключены `CloudAnchorMode` (облачные якоря Google), `GeospatialMode` (VPS Google), `InstantPlacementMode`; оценка освещения тоже выключена. Наш код не обращается ни к одному сервису Google.

⚠️ Честная оговорка: сам ARCore работает через приложение Google «Сервисы Google Play для AR». Google требует от приложений с ARCore сообщать пользователям, что оно используется и подчиняется политике конфиденциальности Google (https://developers.google.com/ar/develop/privacy-requirements) — что именно это приложение Google отправляет о своей работе, мы не контролируем; камеру, позы и метки ARCore без Cloud Anchors / Geospatial на серверы не передаёт. До публикации в магазине — строка об этом в политике конфиденциальности. Для полной независимости от Google (V2) — своё отслеживание движения (ниже).

### Ограничения V0

- Метки не сохраняются: после закрытия экрана оборудование нужно узнать заново (~5 с на «Что это?»).
- Нужен интернет (узнаёт ИИ на сервере). Без сети экран говорит «Нужен интернет для узнавания оборудования» и закрывается.
- Только Android-телефоны с ARCore (список: https://developers.google.com/ar/devices). Без ARCore кнопок нет — работает обычная «Камера-помощник».
- Hit-test нужен «материал»: на гладкой однотонной стене без текстуры ARCore может не найти поверхность — тогда «Подойдите ближе или поводите телефоном». Помогает Depth API (включается, если телефон умеет).
- Табличка ставится в точку, куда смотрел прицел (или в центр рамки ИИ), а не «на оборудование вообще»: если прицел был на стене рядом — табличка там.
- Узнавание — по одному кадру; оборудование, которого нет в реестре, таблички не получает («Не узнал»).
- Журнал: табличка, поставленная автоматически, записывается как «узнал с первого раза»; «Убрать метку» переписывает итог на «отклонено» (V0 не спрашивает, почему убрали).
- Рамка от ИИ (блок 2) **не измерена** на живой модели: новая версия функции ещё не выложена. Замер — `tools/ar/box_probe.mjs` (8 нарисованных сцен с известным местом оборудования). Плохо — выключить секретом `YANDEX_VISION_BOX = off`, метки останутся в точке прицела.
- На эмуляторе и без телефона ничего не проверено: кадр для презентации снимает владелец с телефона.

## V1 — метки, сохранённые у нас

Идея: когда метка поставлена (V0), сохранить у нас **«отпечаток» места** — по чему её можно найти снова, — и при следующем входе находить метки по кадрам без «Что это?».

1. **Отпечаток** (на телефоне, OpenCV — Apache 2.0): ключевые точки и дескрипторы (ORB / AKAZE) нескольких кадров вокруг метки + 3D-координаты точек из ARCore (глубина / hit-test) + поза метки относительно них. Без фото: только числа, по которым картинку не восстановить. Таблица вида `ar_spots` (компания, помещение, оборудование, отпечаток, версия) под RLS + Storage в нашем проекте — миграция V1.
2. **Повторное нахождение**: геозона → объект, план этажа и «Где я» → помещение → загрузить отпечатки только этого помещения (их немного) → сопоставить дескрипторы текущего кадра (сопоставление + `solvePnPRansac` OpenCV) → поза телефона относительно сохранённого места → метки встают сами. Не нашли за ~10 с — подсказка «Что это?» (V0 как запасной путь).
3. **Обновление**: отпечаток дополняется при каждом удачном нахождении (освещение, мебель меняются).

Что даёт: метки «живут» между сессиями, подрядчик видит их сразу; сервер нужен только для загрузки отпечатков помещения (можно заранее, для работы без сети).

## V2 — свой VPS

- **3D-карта помещения** из видео обхода: structure-from-motion — **COLMAP (BSD)**, обработка у нас (сервер в стране клиента, например Yandex Cloud) или у клиента.
- **Локализация кадра**: признаки и сопоставление — **OpenCV (Apache 2.0)**, **LightGlue (Apache 2.0)** с открытыми признаками (DISK / ALIKED — лицензии весов проверить до использования).
- **Своё отслеживание движения** вместо ARCore (визуально-инерциальная одометрия) — чтобы не зависеть от «Сервисов Google Play для AR» и работать на любых телефонах.
- **Не использовать**: SuperPoint (некоммерческая лицензия, в том числе веса LightGlue для SuperPoint), ORB-SLAM3 (GPLv3 — заразит закрытый код).
- Сравнение — с эталоном Niantic (шаг 28): время до «Точно», точность, работа при другом освещении.
